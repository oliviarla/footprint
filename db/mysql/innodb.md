# InnoDB 스토리지 엔진

## 주요 특징

#### 프라이머리 키에 의한 클러스터링

* 모든 테이블은 프라이머리 키(PK)를 기준으로 클러스터링되어 저장된다.
* 클러스터링 인덱스가 있으므로 PK를 이용한 범위 탐색은 매우 빨리 수행된다.
* 모든 세컨더리 인덱스는 프라이머리 키 값을 논리적인 주소로 사용한다.

#### 외래 키 지원

* 여러 테이블에 대한 데이터 무결성을 보장하기 위해 외래 키를 스토리지 엔진 레벨에서 지원한다.
* 부모 테이블과 자식 테이블의 외래 키 칼럼에 대해 모두 인덱스 생성이 필요하고, 외래 키를 포함한 데이터를 추가할 때, 실제 연관 데이터가 존재하는지 확인해야 하므로 락이 여러 테이블에 거쳐 점유되다보니 데드락이 발생할 위험도 있다.

#### MVCC(Multi Version Concurrency Control)

* 레코드 레벨의 트랜잭션을 지원하기 위해 사용하는 방식으로, 락을 사용하지 않는 일관된 읽기 기능을 제공한다.
* 언두 로그(Undo Log)를 사용해 락 없이도 트랜잭션에서 변경(커밋)되기 전의 데이터를 읽는 기능을 제공한다.
* 값이 변경되었지만 커밋되기 전인 상태에서 InnoDB 버퍼 풀의 데이터는 갱신되어 있지만, 기존의 값은 언두 로그에 저장되어 있다.
* 롤백을 실행하면 InnoDB의 언두 영역에 있는 데이터를 InnoDB 버퍼 풀로 복구한다. 이후 해당 언두 영역을 필요로 하는 트랜잭션이 없으면 백업 데이터는 삭제된다.
* 트랜잭션이 길어질수록 관리해야 하는 예전 버전의 데이터가 많아져 언두 영역의 데이터가 많아질 수 있다.

#### 자동 데드락 감지

* 락이 교착 상태에 빠지지 않았는지 락 대기 목록을 그래프(Wait-for List) 형태로 관리한다.
* 데드락 감지 스레드가 주기적으로 교착 상태에 빠진 트랜잭션을 강제 종료시킨다.
* 언두 로그 레코드를 적게 가진 트랜잭션이 먼저 롤백의 대상이 된다.
* 스레드가 락 목록을 조회할 때 변경되지 않도록 자체 락을 걸기 때문에, 이 스레드가 느려지면 서비스 쿼리를 처리중인 스레드가 대기할 수 있다. 특히 동시에 많은 트랜잭션이 실행되는 경우에는 성능 저하가 심해질 수 있다.&#x20;
* 데드락 감지 스레드를 비활성화하고, 데드락 발생 시 일정 시간이 지나면 자동으로 요청이 실패하게 설정할 수도 있다.

#### 자동화된 장애 복구

* MySQL 서버가 시작될 때, 완료되지 못한 트랜잭션이나 디스크에 일부만 기록된 데이터 페이지에 대해 복구 작업이 자동으로 진행된다.
* 자동으로 복구될 수 없는 파일 손상이 있다면 MySQL 서버는 종료된다. 이 경우 `innodb_force_recovery` 설정값을 조절하며 재시작해봐야 한다. 서버가 시작되었다면 데이터를 덤프하여 새로운 서버로 구축하면 된다.

#### 버퍼 풀

* 디스크의 데이터 파일이나 인덱스 정보를 메모리에 캐싱하는 공간이다.
* 변경된 데이터를 모아서 처리하면 랜덤한 디스크 작업을 줄일 수 있다.
* 버퍼 풀 크기를 결정해야 하는 경우 처음에는 전체 메모리의 50% 정도만 버퍼 풀 크기로 잡고, 다른 스레드나 프로세스, 운영 체제의 사용량이 적다면 점차 늘리는 것이 좋다.
* 버퍼 풀에 대한 락 경합을 낮추기 위해 여러 개의 버퍼 풀 인스턴스로 나누어 관리할 수도 있다.

## 버퍼 풀

### 구조

* 프리 리스트
  * 사용자 데이터로 채워지지 않은 비어 있는 페이지 목록을 저장한다.
  * 사용자 쿼리로 인해 디스크에서 페이지를 읽어와야 하는 경우 여기에서 페이지를 사용한다.
* LRU 리스트
  * LRU(Least Recently Used), MRU(Most Recently Used) 리스트가 결합된 형태이다.
  * 디스크에서 읽어온 페이지를 최대한 오랫동안 InnoDB 버퍼 풀에 유지하는 것이 목적이다.
* 플러시 리스트
  * 디스크로 동기화되지 않은 데이터를 가진 더티 페이지의 변경 시점 기준 페이지 목록을 관리한다.
  * 한 번 변경이 가해진 데이터 페이지는 이 리스트에 의해 관리되며 특정 시점이 되면 디스크로 기록해야 한다.

### 리두 로그와 버퍼 풀

* 리두 로그
  * 1개 이상의 고정 크기 파일을 연결해 순환 고리처럼 사용한다.
  * 데이터 변경이 계속해서 발생하면 새로운 로그 엔트리로 덮어쓰일 수 있기 때문에 사용 가능한 공간과 이미 사용 중인 공간을 구분해서 관리한다.
  * 활성 리두 로그는 현재 사용 중인 공간을 의미한다.
  * 리두 로그의 파일 공간은 계속 순환되어 재사용되지만 로그 엔트리가 기록될 때 계속해서 증가하는 LSN(Log Sequence Number)를 갖게 된다.
* 디스크에서 읽어온 후에 변경이 발생한 페이지인 더티 페이지는 리두 로그 엔트리와 매핑된다.&#x20;
* InnoDB 엔진은 주기적으로 체크포인트 이벤트를 발생시켜, 해당 시점의 LSN보다 작은 값을 가진 리두 로그와 버퍼 풀의 더티 페이지를 디스크로 동기화한다.
* 가장 최근 체크포인트 지점의 LSN이 활성 리두 로그 공간의 시작점이 되고, 이 시작점 LSN과 마지막 로그 엔트리의 LSN의 차이가 활성 리두 공간의 크기(checkpoint age)가 된다.
* 리두 로그나 버퍼 풀 둘 중 하나의 크기만 너무 크게 잡은 경우, 버퍼 풀에 보관 가능한 더티 페이지의 수가 줄어드므로 적절한 비율을 유지해야 한다.

### 버퍼 풀 플러시

* 버퍼 풀의 더티 페이지를 디스크에 플러시하는 과정에서 디스크 쓰기 급증이 발생하지 않도록 다음과 같이 백그라운드 작업을 진행한다.
  * 플러시 리스트 플러시
    * 오래된 리두 로그 엔트리가 사용하는 공간을 비우려면 InnoDB 버퍼 풀의 더티 페이지가 먼저 디스크로 동기화되어야 한다.
    * 한꺼번에 많은 더티 페이지를 디스크에 기록하면 사용자의 쿼리 처리에 영향을 미칠 수 있으므로 시스템 변수를 튜닝하는 것이 좋다.
    * 더티 페이지를 디스크로 동기화하는 **클리너 스레드**의 개수를 조절할 수 있는데, 기본적으로 버퍼 풀 인스턴스의 값과 동일하게 두는게 좋다.
    * 일반적으로 InnoDB 버퍼 풀은 더티 페이지를 많이 가질수록 디스크 쓰기 작업을 버퍼링하여 효과를 극대화할 수 있다.
    * 더티 페이지가 특정량 이상 늘어나는 시점에 디스크 쓰기 폭발(Disk IO Burst)가 발생할 수 있기 때문에, 일정 수준 이상의 더티 페이지가 발생하면 미리미리 디스크에 조금씩 기록해두는 것이 좋다.
    * 어댑티브 플러시
      * InnoDB는 기본적으로 어댑티브 플러시 기능을 사용한다.
      * 자동으로 리두 로그의 증가 속도를 분석해 적절한 수준의 더티 페이지가 버퍼 풀에 유지되도록 디스크 쓰기를 진행한다.
      * 전체 리두 로그 공간에서 활성 리두 로그 공간이 10%를 넘는 경우 어댑티브 플러시 기능이 활성화된다.
    * HDD를 사용하는 경우 디스크 기록 시 근접한 페이지 중 더티 페이지가 있다면 함께 묶어 디스크에 기록해주는 기능이 있다.
  * LRU 리스트 플러시
    * 사용 빈도가 낮은 데이터 페이지를 제거해 새로운 페이지를 읽어올 공간을 만든다.
    * 한 번에 스캔할 페이지 개수를 시스템 변수로 지정할 수 있다.
    * 더티 페이지는 디스크에 동기화하게 만들고, 클린 페이지는 프리 리스트 페이지로 옮긴다.

### 백업과 복구

* 쿼리 요청이 빈번한 서버의 경우 셧다운했다가 다시 시작하면 버퍼 풀이 워밍 업되지 않은 상태이므로 쿼리 처리 성능이 현저히 낮아질 수 있다.
* 서버를 셧다운하기 전 버퍼 풀의 상태를 백업해두고 다시 시작 시 이를 복구할 수 있다.

```
SET GLOBAL innodb_buffer_pool_dump_now=ON;
SET GLOBAL innodb_buffer_pool_load_now=ON;
```

* 백업 시 LRU 리스트에 적재된 데이터 페이지의 메타 정보만 저장해두기 때문에 백업 파일의 용량이 작고 빠르게 작업이 완료된다.
* 실제 데이터는 디스크에서 다시 읽어와야 하므로 버퍼 풀 적재 작업은 오래 걸릴 가능성이 높으며 디스크 읽기 작업을 많이 수행할 수 있기 때문에 이 작업 도중 서비스를 재개하는 것은 좋지 않다.
* `innodb_buffer_pool_dump_at_shutdown`, `innodb_buffer_pool_load_at_startup` 설정을 MySQL 서버 설정 파일에 넣어두면 자동으로 종료, 재구동 시 백업과 복구 작업을 진행한다.

### 적재 내용 확인

* `information_schema` 데이터베이스의 `innodb_tables`, `innodb_indexes`, `innodb_cached_indexes` 테이블을 활용하여, 테이블의 인덱스별로 데이터 페이지가 얼마나 버퍼 풀에 적재되어 있는지 확인할 수 있다.

### Double Write Buffer

* 리두 로그는 공간의 낭비를 막기 위해 페이지의 변경된 내용만 기록한다.
* 더티 페이지를 디스크 파일로 플러시할 때 하드웨어/시스템 오류로 일부만 기록되면, 해당 페이지의 내용을 복구할 수 없는 partial page 혹은 torn page 상태가 된다.
* 이러한 문제를 막기 위해 Double-Write 기법을 사용한다.
  * 실제 데이터를 변경하기 전, 더티 페이지를 묶어 DoubleWrite 버퍼에 기록해둔다.
  * InnoDB 스토리지 엔진은 각 더티 페이지를 적당한 파일 위치에 랜덤으로 저장한다.
  * 재시작될 때 항상 DoubleWrite 버퍼의 내용과 데이터 파일의 페이지들을 비교해 다른 내용을 담고 있는 페이지가 있다면 DoubleWrite 버퍼의 내용을 데이터 파일 페이지에 복사한다.
  *   성능은 떨어질 수 있으나 데이터 무결성이 중요한 경우 활성화하는 것이 좋다.

      > 데이터 무결성이 중요한 경우 InnoDB 리두 로그, 복제 목적 바이너리 로그 등을 동기화하는 것도 중요하다.

## 언두 로그

### 특징

* 언두 로그는 데이터를 변경했을 때 실제 데이터는 변경되고, 변경되기 전 데이터를 별도로 보관하는 공간이다.
* 트랜잭션을 보장하기 위한 목적으로 사용된다.
  * **트랜잭션 롤백 대비:** 트랜잭션이 롤백되어 변경되기 전 데이터로 되돌려야 할 때 사용한다.
  * **트랜잭션 격리 수준 보장**: 트랜잭션 격리 수준에 따라 변경중인 레코드를 읽지 않고 언두 로그에 백업해둔 데이터를 읽어 반환할 때 사용한다.
* 트랜잭션이 완료되었다고 해서 해당 트랜잭션이 생성한 언두 로그를 즉시 삭제할 수는 없다. 특정 트랜잭션이 실행중이고 완료되지 않았다면, 다른 트랜잭션들에서 만들어낸 언두 로그들은 계속 보존된다.
* UPDATE, DELETE 문장으로 인한 언두 로그는 MVCC와 롤백, 데이터 복구를 위해 사용되지만, INSERT 문장으로 인한 언두 로그는 롤백, 데이터 복구만을 위해 사용된다.
* 언두 로그가 얼마나 증가했는지 항상 모니터링하는 것이 좋다.

### 언두 테이블스페이스

* 언두 로그가 저장되는 언두 테이블스페이스는 시스템 테이블스페이스 외부의 별도 로그 파일에 기록된다.
* 세그먼트와 슬롯
  * 1\~128개 사이의 롤백 세그먼트로 구성되며, 각 세그먼트는 1개 이상의 언두 슬롯을 가진다.
  * 한 롤백 세그먼트는 InnoDB 페이지 크기 / 16 bytes 개수 만큼의 언두 슬롯을 가진다.
  * 한 트랜잭션은 실행하는 명령에 따라 최대 4개까지의 언두 슬롯을 사용한다.
  * 최대 동시 처리 가능한 트랜잭션 개수는 다음 수식으로 대략 예측할 수 있다.
  * ```
    (InnoDB 페이지 크기) / 16 * (롤백 세그먼트 개수) * (언두 테이블스페이스 개수)
    ```
* Truncate
  * 불필요하거나 과도하게 할당된 공간을 운영체제로 반납하는 것을 의미한다.
  * 자동으로 Truncate하는 경우, Purge Thread가 주기적으로 깨어나 트랜잭션 커밋으로 인해 불필요해진 언두 로그를 삭제한다. 옵션을 통해 주기를 조절할 수 있다.
  * 수동으로 Truncate하는 경우, 직접 언두 테이블스페이스를 비활성화하고 퍼지 스레드가 비활성 상태의 언두 테이블스페이스의 불필요한 공간을 잘라낼 때 까지 기다린다. 작업이 완료된 이후 다시 활성화시켜야 한다. 언두 테이블스페이스가 최소 3개 이상은 되어야 이 방식을 사용할 수 있다.

## 체인지 버퍼

* 데이터가 삽입되거나 삭제되는 경우 인덱스를 업데이트해야 한다.
* 인덱스 업데이트 작업에는 랜덤하게 디스크를 읽는 작업이 필요하므로 많은 자원을 소모할 수 있다.
* 이를 효율적으로 처리하기 위해 인덱스 페이지가 버퍼 풀에 없는 경우 체인지 버퍼라는 임시 메모리 공간에 저장해두고  나중에 백그라운드로 동작하는 **체인지 버퍼 머지 스레드**가 처리한다.
* 유니크 인덱스의 경우 반드시 중복 여부를 체크한 후 사용자에게 응답을 주어야 하므로 체인지 버퍼를 사용할 수 없다.
* 기본적으로 InnoDB 버퍼 풀의 25%까지 사용 가능하지만, 최대 50%까지 늘릴 수 있다.

## 리두 로그와 로그 버퍼

### 리두 로그

* 리두 로그는 하드웨어나 소프트웨어 장애로 MySQL 서버가 비정상적으로 종료되었을 때 데이터 파일에 기록되지 못한 데이터를 잃지 않기 위해 기록된다.
* 대부분의 DBMS는 쓰기보다 읽기 성능을 고려한 자료구조를 가지고 있으므로 데이터 파일 쓰기는 디스크 랜덤 액세스가 필요하다.
* 이로 인한 성능 저하를 막기 위해 쓰기 비용이 낮은 자료 구조의 리두 로그를 두어, 나중에 비정상 종료되었을 때 이 내용을 기반으로 서버가 종료되기 직전의 상태로 복구한다.
* 서버가 비정상 종료되는 경우 다음과 같은 일관되지 않은 데이터를 가질 수 있다.
  * 파일에 기록되지 않은 커밋된 데이터
    * ⇒ 리두 로그에 저장된 데이터를 파일에 적용하면 해결된다.
  * 파일에 기록되었지만 롤백된 데이터
  * ⇒ 변경되기 전 데이터를 언두 로그에서 가져와 파일에 적용하면 해결된다. 이 때 리두 로그를 통해 기존에 어떤 상태였는지 확인해야 한다.

### 리두 로그 버퍼링

* 트랜잭션이 커밋될 때 마다 리두 로그가 디스크에 기록되는 것을 권장하지만, 많은 디스크 부하를 유발하지 않도록 일정 주기마다 동기화하도록 설정할 수도 있다.
* 변경 작업이 매우 많은 경우 리두 로그 버퍼링이 필요하다. 로그 버퍼의 크기는 기본값인 16MB 수준에서 설정하는 게 적절하지만, 크기가 큰 데이터를 자주 변경하는 경우 더 큰 값으로 설정 가능하다.
* 데이터를 복구하거나 대용량 데이터를 한 번에 적재하는 경우 리두 로그를 비활성화하여 적재 시간을 단축시킬 수 있다. 작업이 완료되면 잊지않고 리두 로그를 다시 활성화해야 한다.

### 리두 로그 아카이빙

* 데이터 백업 시 실제 데이터 파일과 데이터 파일 복사 중 리두 로그에 쌓인 내용을 함께 저장해야 일관된 상태를 유지할 수 있다.
* 하지만 데이터 변경 작업이 너무 많은 경우 리두 로그가 빠르게 증가하고, 리두 로그 내용을 백업하기 전 덮어쓰여질 수 있다.
* 리두 로그 아카이빙 기능은 데이터 변경이 많아 리두 로그가 덮어쓰이더라도 백업에 실패하지 않도록 한다.
* 로그 파일이 로테이션될 때 복사되는 것이 아니라 리두 로그 파일에 엔트리가 추가될 때 함께 기록된다. 따라서 데이터 변경이 발생하면 즉시 아카이빙된 로그 파일의 크기가 늘어난다.
* 아카이빙을 시작한 세션과 연결이 끊기는 경우 리두 로그 아카이빙을 멈추고 아카이빙 파일도 제거한다.
* 직접 명령을 통해 아카이빙을 멈추는 경우 아카이빙 파일은 삭제되지 않는다. 따라서 필요 시 수동 삭제해야 한다.

## 어댑티브 해시 인덱스

### 특징

* 사용자가 자주 요청하는 데이터에 대해 자동으로 생성하는 인덱스로, B-Tree 검색 시간을 줄여주기 위해 도입되었다.
* B-Tree 인덱스에서 특정 값을 찾는 과정에서 루트 노드를 거쳐 브랜치 노드, 리프 노드까지 찾아가야 하며 동시에 수 천개의 스레드가 이 작업을 수행한다면 성능이 떨어지게 된다.
* **인덱스 키 값(인덱스 고유 번호 + 인덱스의 실제 키 값)**&#xACFC; 해당 인덱스 키 값이 저장된 **데이터 페이지 메모리 주소**의 쌍을 저장하여 자주 접근되는 인덱스의 데이터는 노드를 순회하지 않더라도 조회 가능하다.
* 모든 B-Tree 인덱스에 대한 어댑티브 해시 인덱스는 하나의 해시 인덱스에 저장되기 때문에 인덱스 고유 번호도 함께 저장해야 한다.
* 하나의 메모리 객체이기 때문에 세마포어 경합이 심할 수 있다. 이 경우 파티션 개수를 늘려 경합을 줄일 수 있다.

### 성능

* 어댑티브 해시 인덱스를 활성화하면 동일 요청 대비 CPU 사용률이 줄어들고 초당 쿼리 처리 수가 늘어난다.
* 디스크의 데이터가 InnoDB 버퍼 풀 크기와 비슷해 디스크 읽기가 많지 않은 경우, 동등 조건 검색이 많은 경우, 쿼리가 일부 데이터에 집중되는 경우 효과적이다.
* 데이터 페이지를 버퍼 풀 내에서 접근하는 것을 빠르게 만드는 것이므로, 디스크 접근이 빈번하면 성능 향상이 미비할 수 있다.
* 테이블 삭제 및 변경 작업이 있는 경우 어댑티브 해시 인덱스에서 해당 테이블이 갖는 모든 데이터 페이지 내용을 제거해야 하므로 서버의 처리 성능이 느려질 수 있다.
